========================================================
  AUTO-ANNOTATE GUI - SETUP & RUN INSTRUCTIONS
========================================================

OVERVIEW
--------
The visualizer is the Manual Prompt and Confidence Tuning window.
It lets you load a folder of images, pick a detector and segmenter,
prompt by text or by drawing boxes, and see bounding boxes or
segmentation masks drawn live over your images.

--------------------------------------------------------
SUPPORTED OPERATING SYSTEMS (macOS / Windows / Linux)
--------------------------------------------------------
The app runs on macOS, Windows and Linux. All file paths are derived
portably (autoannotate/config.py anchors everything to the repo root with
os.path.join), so no path edits are needed when you move machines - just
set GROUNDING_DINO_DIR in .env if GroundingDINO lives somewhere unusual.

The ONLY per-OS knob is which compute device runs the Stable Diffusion
background-variation step. It lives in autoannotate/config.py under the
header "PER-OS COMPUTE-DEVICE CONFIG", as commented lines for each OS:

  macOS (Apple Silicon/Intel) : AUTOANNOTATE_SD_DEVICE = "cpu"  (8GB-safe)
                                AUTOANNOTATE_SD_DEVICE = "mps"  (>8GB Macs)
  Windows / Linux + NVIDIA GPU: AUTOANNOTATE_SD_DEVICE = "cuda" (fastest)
  Windows / Linux, CPU only   : AUTOANNOTATE_SD_DEVICE = "cpu"

By default config.py AUTO-DETECTS: macOS -> "cpu" (MPS has hung SD-1.5
inpainting for 15+ min on 8GB), and on Windows/Linux it leaves the value
unset so the SD loader picks CUDA, then MPS, then CPU on its own. To force
a device, uncomment exactly one line for your OS in that block. The
detection/segmentation models (DINO, YOLOE, SAM2/SAM3) choose their own
device automatically and need no setting.

Verify a machine quickly (any OS) with:
  python "GUI and Pipeline/check_environment.py"
It loads no models - it just confirms the Python deps, prints which
compute device the app will use, reports the PyTorch CUDA build/GPU and
GroundingDINO compiled extension, and lists which weight files are present.
Run it inside the activated venv (Step 1).

--------------------------------------------------------
STEP 0 - FRESH MACHINE PREREQUISITES (install these first)
--------------------------------------------------------
Everything below assumes tools a machine with no prior dev work will
NOT have. None of them come from pip. On a machine that already has
them, skip to STEP 1.

a) Git - to clone the repository at all.
     Windows:  https://git-scm.com/download/win  (installer defaults
               are fine; GitHub Desktop also works if you prefer a GUI)
     macOS:    xcode-select --install
     Linux:    sudo apt install git

b) Python 3.13 - the version every requirements file is proven on.
     Windows:  https://www.python.org/downloads/  - in the installer
               KEEP the "py launcher" option ticked; STEP 1's
               `py -3.13` command needs it.
     macOS:    https://www.python.org/downloads/ or
               `brew install python@3.13`
     Linux:    sudo apt install python3.13 python3.13-venv
   Verify:   py -3.13 --version        (Windows)
             python3.13 --version      (macOS/Linux)

Subsection c is WINDOWS/LINUX + NVIDIA GPU ONLY. A CPU-only machine
skips subsection c. Every Windows machine, including Windows 10 CPU-only,
must still complete subsection d because GroundingDINO builds a C++
extension.

c) NVIDIA driver + CUDA Toolkit. These are two different installs and
   BOTH are needed:
   - Driver (runs the models): https://www.nvidia.com/drivers
     An outdated driver is the top cause of
     torch.cuda.is_available() == False; a driver reinstall was
     required on the validation machine.
   - CUDA Toolkit (builds GroundingDINO):
     https://developer.nvidia.com/cuda-downloads
     The toolkit provides nvcc, which compiles GroundingDINO's CUDA
     extension in STEP 4. The driver alone cannot build anything.
   VERSION MATCH RULE: the toolkit version must match the +cuXXX pins
   in requirements-windows11-cuda.txt. The one combination actually validated
   here is CUDA Toolkit 13.2 with torch==2.12.1+cu132, which is what
   that file pins. Install that toolkit and the pins work as written.
   Other toolkits need a torch build that exists for them, and not
   every pairing does; do not just search-and-replace cu132. Look the
   combination up in PyTorch's official install selector first:
   https://pytorch.org/get-started/locally/
   The Windows installer sets the CUDA_PATH environment variable;
   leave it in place. The app reads it at startup to register the
   CUDA DLL folder (see COMMON ERRORS, "DLL load failed").

d) Visual Studio Build Tools (all Windows machines) - the C++ compiler
   used to build GroundingDINO's extension. On CUDA systems, nvcc also
   drives this compiler:
     https://visualstudio.microsoft.com/visual-studio-build-tools/
   In the installer select the "Desktop development with C++"
   workload (this includes MSVC v143 and the Windows SDK). The
   validated machine used MSVC 14.51.

With those in place, clone the repo and work from its root:

  git clone <your fork or origin URL>/AutoAnnotate.git
  cd AutoAnnotate

--------------------------------------------------------
STEP 1 - ONE-TIME SETUP: PYTHON ENVIRONMENT
--------------------------------------------------------
Make sure you are using the project's virtual environment.

From the repo root:

  source .venv/bin/activate          # Mac/Linux
  .venv\Scripts\activate             # Windows (cmd)

If the venv doesn't exist yet, create it first:

  There is no one-size-fits-all requirements file. Pick the one for your OS:
    - requirements-macos.lock    macOS / Apple Silicon (MPS): exact pins
    - requirements-windows10-cpu.txt
                                  Windows 10 CPU-only: exact proven pins
    - requirements-windows11-cuda.txt   Windows 11 + NVIDIA CUDA: pinned CUDA torch
    - requirements.txt           generic floors: Linux, or any OS (advanced)

  macOS:
    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements-macos.lock

  Linux:
    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt
  The macOS lock is macOS-ONLY (it freezes CPU/MPS torch and wheels
  built for Mac); do not use it on Linux. On Linux + NVIDIA, after the
  install above, swap in the CUDA torch build the same way Windows
  does:
    pip uninstall -y torch torchvision torchaudio
    pip install torch torchvision --index-url https://download.pytorch.org/whl/cu132
  (match the cuXXX to your toolkit, see STEP 0c), then verify:
    python -c "import torch; print(torch.cuda.is_available())"

  Windows 10 CPU-only (PowerShell), validated with Python 3.13:
    py -3.13 -m venv .venv
    Set-ExecutionPolicy -Scope CurrentUser RemoteSigned   (one-time)
    .venv\Scripts\Activate.ps1
    python -m pip install --upgrade pip
    python -m pip install -r requirements-windows10-cpu.txt

  This exact lock uses torch 2.6.0+cpu with torchvision 0.21.0+cpu. It does
  not require an NVIDIA driver or CUDA Toolkit. It DOES require Visual Studio
  Build Tools with the "Desktop development with C++" workload because DINO
  builds a CPU C++ extension in STEP 4. On a very slow computer, prefer DINO
  (SwinT) + SAM2 (tiny); SwinB is much larger and slower.

  Windows 11 + NVIDIA CUDA (PowerShell), validated with Python 3.13:
    py -3.13 -m venv .venv
    Set-ExecutionPolicy -Scope CurrentUser RemoteSigned   (one-time; lets
                                                           Activate.ps1 run)
    .venv\Scripts\Activate.ps1
    pip uninstall -y torch torchvision torchaudio   (clear any CPU build first)
    pip install -r requirements-windows11-cuda.txt
  From cmd instead of PowerShell, activate with .venv\Scripts\activate.bat
  and skip the Set-ExecutionPolicy step.

  WINDOWS + NVIDIA GPU: requirements-windows11-cuda.txt already pins the CUDA
  torch/torchvision wheels (+cuXXX) and adds the PyTorch CUDA index, so pip
  installs the GPU build instead of the CPU one. The validated combo was
  torch 2.12.1+cu132 on CUDA 13.2 / RTX 4060. If your driver needs a
  different CUDA, change every cu132 in that file to match. Then verify:
    python -c "import torch; print(torch.cuda.is_available())"
  If that prints False, update your NVIDIA driver first (a driver
  reinstall was required on the validation machine) and reinstall.

  NOTE: transformers must stay below 5.x (the platform files pin
  "transformers==4.50.3" / ">=4.40,<5"). transformers 5.x removed a BERT
  method GroundingDINO needs and crashes at DINO model load.

(python-dotenv is already in every requirements file, so no separate
install is needed.)

REPRODUCIBLE INSTALL: the platform files above ARE the reproducible path
(requirements-macos.lock and requirements-windows10-cpu.txt are full tested
environment locks; requirements-windows11-cuda.txt pins the CUDA torch stack).
requirements.txt only pins floors and is for advanced users who want the
newest resolutions. Note: GroundingDINO is NOT in any of them; install it
in STEP 4.

No Jupyter setup is needed. The app is plain Python scripts launched
from the terminal (STEP 5); there is no notebook to run.

--------------------------------------------------------
STEP 2 - ONE-TIME SETUP: CONFIGURE .env
--------------------------------------------------------
.env is NOT in git (it is ignored), so a fresh clone has only
.env.example. Create yours from it:

  cp .env.example .env               # Mac/Linux
  copy .env.example .env             # Windows

This whole step is OPTIONAL: the app runs with no .env at all. Every
value in it has a working default; you edit it only to override one:

  GROUNDING_DINO_DIR=/absolute/path/to/autoannotate study/GroundingDINO

You normally do NOT need to set this: config.py auto-derives it from
the repo root, and it accepts BOTH folder spellings ("autoannotate
study" as git tracks it, and "autoannotate_study" as zips/transfers
sometimes rename it). Set it only if GroundingDINO lives somewhere
unusual.

NOTE (VS Code users): the editor warning about "python.terminal.useEnvFile"
/ terminal environment injection is UNRELATED to the app. The app loads
.env itself via python-dotenv at startup, no editor setting needed. To
confirm your .env values took effect, run check_environment.py: it prints
the effective AUTOANNOTATE_MAX_AREA_FRAC and AUTOANNOTATE_SD_DEVICE.

HF_TOKEN in the .env is OPTIONAL and the running app never uses it.
Every model the app loads is either public (SmolVLM, bert-base-uncased
for DINO, Stable Diffusion 1.5) or already on disk (sam3.pt) or comes
from ultralytics' own server (SAM2, YOLOE) -- none require a token, and
no from_pretrained call passes one. With the weights in place the app
runs fully token-free; you can leave HF_TOKEN blank.

A token is only useful OUTSIDE the app, for the ONE-TIME manual download
of the gated sam3.pt from huggingface.co/facebook/sam3 (you accept the
license there and authenticate the download). Once sam3.pt sits in
"GUI and Pipeline/", nothing in the code reads the token again.

STEP 3 - ONE-TIME SETUP: DOWNLOAD MODEL WEIGHTS
--------------------------------------------------------
The app needs several weight files that are NOT in the repo
(too large for git).

a) GroundingDINO weights
   Destination folder:
     autoannotate study/GroundingDINO/weights/

   Files to download:
     groundingdino_swint_ogc.pth
       -> https://github.com/IDEA-Research/GroundingDINO/releases

     groundingdino_swinb_cogcoor.pth  (only if you use SwinB, ~938 MB)
       -> same releases page

   Until groundingdino_swinb_cogcoor.pth is in place, the "DINO (SwinB)"
   entries in the Detector dropdown auto-grey with a tooltip (same
   mechanism as the SAM3 entries). SwinB "not working" on a fresh
   machine is almost always just this missing weight.

b) SAM 2 weights
   The code uses "sam2_t.pt" loaded by ultralytics SAM.
   Ultralytics auto-downloads sam2_t.pt on first run if you have
   an internet connection. NOTE: it downloads into the CURRENT WORKING
   DIRECTORY (the repo root if you launched from there); move the file
   into "GUI and Pipeline/" afterwards so the app finds it on the next
   run. If it doesn't auto-download, fetch manually:
     https://github.com/ultralytics/assets/releases
   and place sam2_t.pt in "GUI and Pipeline/".

c) SAM 3 weights (for SAM3 detector and SAM3 segmenter)
   Filename: sam3.pt
   Source:   https://huggingface.co/facebook/sam3
             (gated - you must accept the license on HF first)
   Destination: GUI and Pipeline/
   If sam3.pt is missing, the SAM3 entries in both dropdowns auto-grey
   with a tooltip so you cannot accidentally run them.

d) YOLOE weights (for YOLOE-vis and YOLOE-seg one-shot)
   Filenames: yoloe-11l-seg.pt and yoloe-11l-seg-pf.pt
   Source:    https://github.com/ultralytics/assets/releases
   Destination: GUI and Pipeline/

e) LLM weights (only needed for the Automated window)
   The splash screen loads HuggingFaceTB/SmolVLM-256M-Instruct from
   Hugging Face on startup. It is about 0.5 GB and is a public model,
   so it downloads without a Hugging Face token.
   To skip LLM loading (Manual window only, no Automated features):
   see the note in STEP 5 below.

--------------------------------------------------------
STEP 4 - INSTALL GROUNDINGDINO PYTHON PACKAGE
--------------------------------------------------------
GroundingDINO must be installed as a Python package so that
"from groundingdino.util.inference import ..." works.

  pip install --no-build-isolation -e "autoannotate study/GroundingDINO"

IMPORTANT: the --no-build-isolation flag is REQUIRED. GroundingDINO's
setup.py does `import torch` at build time; without this flag pip builds
in an isolated environment that has no torch and the install fails with
"ModuleNotFoundError: No module named 'torch'". Because of this flag,
torch must already be installed (it is, from STEP 1) before you run this.

If you see CUDA/torch errors, make sure your PyTorch version
matches your CUDA driver before installing.

WINDOWS BUILD PREREQUISITES (CUDA path validated on Windows 11, CUDA 13.2,
RTX 4060, VS Build Tools with MSVC 14.51):

  1. Install Visual Studio Build Tools with the "Desktop development
     with C++" workload (provides cl.exe / MSVC v143). This is needed
     for both CPU and CUDA builds; on CUDA machines, nvcc drives cl.exe.
  2. In the venv, install the build helpers first (wheel fixes
     "invalid command 'bdist_wheel'"; ninja was required on the
     validation machine):
       pip install wheel setuptools ninja
  3. Run the pip install command above from PowerShell with the
     folder path quoted (the folder name contains a space).

  The vendored setup.py now adds the MSVC conforming-preprocessor flag
  (/Zc:preprocessor) automatically on Windows; CUDA >= 12.4/13 CCCL
  headers require it. On an older checkout, set it manually before
  building:  $env:CL = "/Zc:preprocessor"

  The extension is built WITH CUDA only when torch can see the GPU
  during the install. If torch.cuda.is_available() is False at build
  time you get a CPU-only extension and DINO silently falls back to
  slow pure-Python deformable attention. Fix torch first (STEP 1), or
  force it with FORCE_CUDA=1 when CUDA is installed but not visible.

  AFTER PULLING THESE FIXES on a machine that built GroundingDINO
  earlier: re-run the pip install command above once so the extension
  is rebuilt from the patched source.

To uninstall later:  pip uninstall groundingdino

--------------------------------------------------------
STEP 5 - RUN THE APP
--------------------------------------------------------
The application code lives in the `autoannotate` package at the repo root:

  autoannotate/config.py    - env, paths, device configuration
  autoannotate/pipeline/    - DINO / YOLOE / SAM / SD wrappers and label I/O
  autoannotate/gui/         - the PyQt5 windows, canvas and dialogs
  autoannotate/optimizer.py - prompt/confidence optimizers

Launch it from a terminal (inside the venv), from the repo root:

  python run_app.py
      -- or --
  python -m autoannotate

That is the whole launch procedure: no IDE or Jupyter session is
involved. The old launcher notebook (auto-annotate-gui.ipynb) has been
retired to junk/.

To verify the install (or a code change) beyond launching, run the
headless regression suite from the repo root. The environment variable
has to be set the way YOUR shell sets one:

  macOS / Linux (bash, zsh):
    QT_QPA_PLATFORM=offscreen python "GUI and Pipeline/test_semiauto_headless.py"

  Windows PowerShell:
    $env:QT_QPA_PLATFORM="offscreen"; python "GUI and Pipeline\test_semiauto_headless.py"

  Windows cmd.exe:
    set QT_QPA_PLATFORM=offscreen && python "GUI and Pipeline\test_semiauto_headless.py"

Expect every check to pass, e.g. "520/520 checks passed" (the total
grows as tests are added; what matters is passed == total). For
live-GUI verification, walk "GUI and Pipeline/MANUAL_TEST_CHECKLIST.md".

NOTE: The app opens a PyQt5 window. This requires a display.
  - On a local Mac/Windows machine: works out of the box.
  - On a remote server/SSH: you need X11 forwarding or a VNC session.

NOTE - The prompt-suggestion VLM (SmolVLM) now loads LAZILY:
  It is no longer loaded on the splash screen. It loads automatically the
  first time you actually use prompt generation (the Automated window's
  "Generate Prompts", or any path that calls it). So a Manual-only session
  never pays its ~0.5 GB or its load wait, and startup is faster. If the
  VLM can't load, prompt generation simply returns nothing and the rest of
  the app is unaffected.

--------------------------------------------------------
STEP 6 - USING THE VISUALIZER (Manual Window)
--------------------------------------------------------
1. The splash screen appears and loads the SmolVLM model in the
   background. Wait for "Model loaded successfully." in the log, then
   the main menu opens automatically.

2. Click "Manual Prompt and Confidence Tuning".

3. Click "Select Image Folder" -> choose a folder of .jpg/.png images.

4. Click "Select Output Folder" -> choose where annotation files will
   be saved (bounding box labels go to output/boxes/,
   segmentation masks go to output/segments/).

5. Pick a detector and a segmenter from the dropdowns:

   Detector options:
     - DINO (SwinT)       - text prompts, returns boxes
     - DINO (SwinB)       - heavier DINO variant, same interface
     - YOLOE-vis          - visual prompts (drawn boxes), one-shot:
                             returns boxes AND masks in a single pass
     - YOLOE-seg          - one-shot detector + mask generator;
       (one-shot)            pair with segmenter "(none)"
     - SAM3 (one-shot)    - text OR drawn boxes; returns boxes and masks

   Segmenter options:
     - SAM2 (tiny)        - default; converts detector boxes to masks
     - SAM3               - higher-quality; same role as SAM2
     - (none)             - only valid with YOLOE-seg (one-shot)

   Greyed-out entries mean the corresponding weight file is missing -
   hover the entry to see which file and where to put it.

6. Pick a prompt mode (radio above the prompt entry):

   - Text   - type class names ("red apple, leaf"); the detector
              finds them in the image. Used with DINO and SAM3.
   - Boxes  - draw yellow prompt boxes directly on the image; the
              detector treats them as visual prompts. REQUIRED for
              YOLOE-vis. Optional for SAM3 and YOLOE-seg.

   Drawn boxes route to the YELLOW prompt bucket when the detector
   actually consumes prompts; otherwise drags become GREEN annotation
   boxes. The bucket re-evaluates whenever you change detector or
   prompt mode.

   MULTI-CLASS PROMPTS (one model run, no re-running per class):
   in Text mode the Prompts section holds one FIELD per class; click
   "+ Add prompt" for another (up to 5 fields; the button greys out at
   the cap). A single field can still be comma-separated when the names
   are synonyms for one class. Every class is detected in a SINGLE
   pass; each detection keeps its class id (0, 1, ... in field order)
   all the way into the saved YOLO label files, and each class gets its
   own outline color on screen (class 0 keeps the classic magenta).
   Three key files are written with the labels: classes.txt (one bare
   name per line, importable), class_colors.txt (the color key: one
   commented column-header line, then one aligned row per class), and
   class_legend.png next to the annotated_<model> review folders. Hover
   the info dot beside the Prompts header for the live color legend; it
   stays visible when the section is collapsed.

   NEGATIVE PROMPTS ("+ Add negative" fields): things you do NOT want
   annotated, e.g. positive "blueberry" with negative "leaf". Negatives
   are detected in the SAME single pass; every negative hit is
   discarded and any positive detection that overlaps a negative hit
   is dropped too. Works with the text-prompt detectors (DINO,
   YOLOE-seg text, SAM3 text). Empty negative fields change nothing
   and never block a run.

   BOX-MODE CLASSES: in Boxes mode the text fields hide and a
   "Draw box as:" dropdown appears with up to 5 colored classes
   (rename them and set the count via Classes...). Names last for the
   APP SESSION: they survive moving between images and going back to
   the main menu, but a fresh launch always starts from one unnamed
   class; nothing is written to disk. Drawn prompt boxes carry the
   class selected WHEN DRAWN, hand-drawn annotation boxes keep theirs
   too, and "Draw Negative Box" draws red suppression boxes. SAM3 box
   prompts run one pass per class under the hood (its predictor is
   single-concept per call); the terminal prints a
   "[SAM3 multi-class] N passes" line when that happens. Lowering the
   class count below a class already drawn on the current image is
   refused with a message naming the blocking class; delete those
   boxes first.

7. Check either "Bounding Box" or "Segmentation" to control the
   display mode.

8. Adjust the sliders:
   - Detection threshold : detector confidence cutoff (0-100)
   - Mask threshold      : segmenter confidence cutoff (0-100);
                           ignored when the detector is one-shot
                           with "(none)" as the segmenter
   - Max detection size  : drop any detection covering more than this
                           fraction of the image (0.05-1.00)

   PER-CLASS SETTINGS (appears only with 2+ classes): each class keeps
   its OWN three values. A berry class wants a low max detection size,
   a leaf class a high one, so one-size-fits-all sliders are wrong for
   mixed-size classes. Pick a class in the Per-Class Settings section
   and move its sliders; they apply immediately. The classic three
   sliders become "Global sliders (all classes)": moving one no longer
   applies live; an "Apply to All Classes" / "Revert" row appears, and
   Apply (after a confirmation, since it overwrites every class's
   individual values) is the only way it takes effect. Regenerate and
   Auto Annotate Remaining REFUSE to run while a global change sits
   unapplied. With one class none of this exists and the sliders behave
   exactly as they always did.
   Under the hood, single-pass detectors (DINO, YOLOE, SAM3 text) run
   once at the loosest class threshold and each detection is then
   re-checked against its own class's values; SAM3 box prompts already
   run one pass per class, so each pass takes its class's confidence
   directly. One limitation: DINO's text_threshold (driven by the Mask
   slider) is a single-pass token filter and uses the loosest class's
   value for every class.

9. Click "Auto annotate" to run the selected pipeline on the current
   image and see results overlaid.

   First SAM3 text call loads ~hundreds of MB - the action buttons
   grey out for several seconds. This is normal; cached on subsequent
   calls.

10. Edit annotations directly on the canvas:
    - Drag to draw a new annotation (rect or polygon depending on
      display mode).
    - Click an annotation to select it; press the red X badge to
      delete.
    - Rect annotations have corner/edge handles for resize.
    - Image Resize can stay ON while you draw and edit: scrolling pans
      the zoomed image and the left button keeps drawing. Zoom with a
      trackpad pinch or Ctrl/Cmd+scroll. The Image Resize dropdown has
      a Trackpad/Mouse input picker (trackpads pan on both axes with a
      two-finger scroll; mice pan vertically with the wheel and
      sideways with Shift+wheel). The same picker and bindings apply
      in the side-by-side viewer.

11. Click "Next Image" to step through the folder. "Previous Image"
    goes BACK one image WITHOUT re-running the model: the previous
    image's saved annotations are reloaded from the label files exactly
    as you left them, so anything you trimmed or edited stays edited
    (a fresh model run would overwrite that work). Both buttons save
    the current image first. Previous is unavailable on the first
    image (nothing before it) and after the folder is finished (the
    folder deselects on completion, as before).

12. When happy with the prompt and slider settings, click
    "Auto Annotate Remaining" to batch-annotate the rest of the folder.
    This batch path runs the SAME detector + segmenter you selected in
    the dropdowns (via _run_detector / _run_segmenter) on every remaining
    image - YOLOE, SAM3 and DINO pipelines all work here, not just DINO.
    Each image's labels go to output/boxes/ and masks to output/segments/,
    overwriting any existing label for that image.
    - Text prompt carries automatically (it is reused on every image).
    - To carry the box prompts you drew on this image across the whole
      folder, turn on "Use First Image as Prompt" first (enabled only for
      the box-capable detectors: YOLOE-vis/-seg and SAM3; DINO is
      text-only so the toggle is greyed there).
    - INCLUDE EARLIER IMAGES (recycle toggle): by default the batch only
      covers the images from here forward; images you already stepped
      past are omitted. Turn "Include Earlier Images" ON to append those
      earlier images to the END of the run, so starting a batch halfway
      through a folder still covers all of it. Their existing label
      files are overwritten like any other batch target.
    - ZERO-detection retry: if an image gets no detections, the detector
      automatically RETRIES ONCE at a lower threshold (det + mask x 0.5,
      tunable via AUTOANNOTATE_RETRY_FACTOR). It is a single bounded retry,
      never a loop.
    - REVIEW folder: images that are STILL empty after the retry, or that
      error out, are COPIED (never moved) into a review folder so you can
      fix them by hand:
        output/_review/boxes/      (no detections - detection-stage problem)
        output/_review/segments/   (boxes found but no masks - seg-stage)
        output/_review/review_report.csv   (image, stage, status, reason,
                                            detector, prompt, thresholds)
      The _review folder is rebuilt every run (a clean run removes it). The
      end-of-run popup reports "Failed: N", "Empty (needs review): N", and
      the review-folder path.
    - REVIEW SIDE BY SIDE: turn this toggle ON before starting the batch
      and the side-by-side viewer opens as soon as the run finishes, with
      the input images on one side and this run's annotated images on the
      other, both folders already loaded. Which overlay it shows follows
      the Bounding Box / Segmentation checkboxes:
        Bounding Box only    -> output/annotated_<model>/boxes
        Segmentation only    -> output/annotated_<model>/masks
        both ticked          -> you are asked which one (or Skip)
        neither / not saved  -> whichever the run actually produced
      It opens after both end-of-run popups, and closing it (Back, Esc, or
      the window's X) returns you to the annotation window rather than the
      main menu. A canceled run still opens the viewer for what did finish;
      a run that annotated nothing does not.
    - GPU OUT OF MEMORY: if a detector or segmenter call runs the GPU out
      of memory, the app frees EVERY resident model (the detector/segmenter
      cache, the SAM3 text predictor, and the Stable Diffusion pipeline,
      which otherwise stays on the card for the rest of the session once
      you have generated a variation) and retries that image once before
      giving up. An image that fails anyway is reported with the two knobs
      to turn (AUTOANNOTATE_MODEL_BUDGET_GB, AUTOANNOTATE_BATCH_CHUNK)
      instead of a bare torch error.

--------------------------------------------------------
TUNING KNOBS (optional environment variables)
--------------------------------------------------------
All optional. Defaults reproduce the original behavior, so you only set
these to tune speed/memory. Set them in your shell before launching, or in
autoannotate/config.py (its PER-OS block already sets
AUTOANNOTATE_SD_DEVICE).

  AUTOANNOTATE_SD_DEVICE        cpu | mps | cuda. Stable Diffusion compute
                                device. Default: auto (macOS->cpu; else
                                CUDA>MPS>CPU). See the OS section above.

  AUTOANNOTATE_MODEL_BUDGET_GB  Soft RAM budget for resident detection/
                                segmentation models; least-recently-used
                                models are evicted when a load would exceed
                                it. Default on CUDA: 55% of the card's total
                                VRAM (so DINO + SAM3 + YOLOE cannot all sit on
                                an 8 GB card at once, which is what ran batch
                                runs out of memory). Default elsewhere: unset
                                = unbounded. An explicit value always wins,
                                including 0 to restore unbounded. Set ~4.5 on
                                an 8 GB Mac to stop SAM3 (~3.3 GB) co-residing
                                with other heavy models.
                                Auto Annotate Remaining is EXEMPT: a batch run
                                holds its own detector and segmenter for the
                                whole run, so the two never evict each other
                                between the chunked detect and segment passes.
                                Offloading is for a detector/segmenter SWITCH,
                                where the dropped model is not coming back; mid
                                run it would only reload multi-GB weights the
                                next chunk asks for again. Models the running
                                pipeline does NOT use are still reclaimed.
                                If a batch runs out of memory anyway, the card
                                has proved it cannot hold both, so the exemption
                                is dropped for the rest of that run and the app
                                prints a "[model-cache] ... wants N GB against
                                an M GB budget" line naming the tradeoff. Raise
                                this variable, set it to 0, or pick a lighter
                                pipeline if you would rather not pay it.

  PYTORCH_CUDA_ALLOC_CONF       Set to expandable_segments:True by
                                autoannotate/__init__.py before torch is
                                imported, so a long batch run does not
                                fragment VRAM into blocks it can never merge.
                                This is a torch variable, not ours: export
                                your own value to override it entirely.

  AUTOANNOTATE_KEEP_MODELS_WARM 1 = keep every model cached across detector/
                                segmenter switches (faster switching, more
                                memory). Default: 0 = offload the models the
                                new pipeline no longer uses on each switch.

  AUTOANNOTATE_BATCH_CHUNK      Images to DETECT before switching to the
                                SEGMENT pass in a two-stage (detector ->
                                separate segmenter) batch run, so one heavy
                                model is resident per pass. Default: 8.

  AUTOANNOTATE_RELEASE_EVERY    Release GPU/MPS memory every Nth inference.
                                Default: 4 on CUDA, 1 (every time) on MPS and
                                CPU. MPS keeps 1 because the 8 GB Mac needs it.
                                CUDA relaxes because empty_cache() hands blocks
                                back to the driver for the next allocation to
                                fault in again, and expandable_segments (above)
                                now covers the fragmentation this was guarding
                                against. Lower it to 1 if a long CUDA run creeps
                                up on the card. Once a session has actually run
                                out of memory the app drops to 1 by itself for
                                the rest of that session, whatever this is set
                                to.

  AUTOANNOTATE_RETRY_FACTOR     Multiplier for the single lower-threshold
                                retry on an empty detection in Auto Annotate
                                Remaining. Default: 0.5 (half). Clamped to
                                between 0 and 1.

  AUTOANNOTATE_MAX_AREA_FRAC    Drop any single detection whose box covers
                                more than this fraction of the image (a
                                spurious whole-/large-image match). Applied to
                                ALL detectors. Default: 0.5 (drops anything
                                covering more than half the image; tuned for
                                small-object fruit/berry folders). RAISE it
                                to ~0.8-0.9 for genuinely large subjects, or
                                LOWER it to ~0.3 for tiny-object / texture
                                folders (e.g. fescue/grass). Clamped to
                                (0, 1]. check_environment.py prints the
                                effective value so you can confirm your .env
                                took effect.

  AUTOANNOTATE_DINO_RESCUE      1 = on an otherwise-empty DINO image, keep
                                the low-confidence candidates above a small
                                floor (review them) instead of returning
                                nothing. Default: 0 (off).

  AUTOANNOTATE_DEBUG            1/true = verbose diagnostics ([model-cache],
                                [_get_model], evictions, etc.). Read from
                                the environment or .env in
                                autoannotate/config.py. Default: off.

Not an env var -- a code flag (edit autoannotate/pipeline/dino.py):
  DINO_SCORE_DIAGNOSTICS        False by default. Set True to print DINO's
                                top raw detection scores per image (doubles
                                DINO inference time; use only to calibrate
                                the confidence slider).

--------------------------------------------------------
COMMON ERRORS & FIXES
--------------------------------------------------------
"GroundingDINO not found. Tried: ..."
  -> Normally auto-derived; both "autoannotate study" and
     "autoannotate_study" folder names are accepted. If the folder truly
     lives elsewhere, set GROUNDING_DINO_DIR in .env (Step 2).

"ModuleNotFoundError: No module named 'groundingdino'"
  -- the splash screen opens, then clicking into Manual mode crashes
  -> Your machine has BOTH folder spellings and they have drifted apart.
     Run:  python "GUI and Pipeline/check_environment.py"
     and read the "GroundingDINO install integrity" section. It prints
     which tree Python imports from, which tree pip was installed
     against, which one GROUNDING_DINO_DIR resolves to, and exactly
     which source files are missing.

     What causes it: only "autoannotate study" (with the space) is
     tracked by git. If "pip install -e" was pointed at the
     "autoannotate_study" copy instead, then git updates refresh the
     tracked tree while the copy Python actually imports goes stale. It
     can end up holding just the compiled _C extension with the .py
     sources gone, which is this error.

     The compiled extension is NOT the problem and does not need
     rebuilding.

     READ THIS BEFORE REINSTALLING ANYTHING. The compiled _C extension
     and the weights/*.pth files are excluded by .gitignore (*.so,
     *.pyd, weights/). They therefore exist ONLY in the tree they were
     built or downloaded into, which on a machine with this problem is
     usually the UNTRACKED copy. Reinstalling against the tracked copy
     as a first move abandons both, and the CUDA extension is slow to
     rebuild. check_environment.py prints which copy holds them.

     Fix it this way:

       1. Copy the untracked artifacts into the tracked copy:
            groundingdino/_C.*        (the compiled extension)
            weights/*.pth             (the DINO checkpoints)
          from "autoannotate_study/GroundingDINO"
          into "autoannotate study/GroundingDINO".

       2. Repoint the editable install at the tracked copy:
            pip install --no-build-isolation -e "autoannotate study/GroundingDINO"

       3. Rename the untracked copy aside and re-run check_environment.
          Git now maintains the only tree that matters.

     Alternative, if you would rather not move anything: make the two
     spellings the SAME directory so they can never diverge again.
     Rename the untracked copy away first, then at the repo root:
       Windows (Administrator):
         mklink /J "autoannotate_study" "autoannotate study"
       macOS/Linux:
         ln -s "autoannotate study" autoannotate_study

     Quickest patch (does not fix the cause): copy the missing .py
     files across from the tracked copy and leave the _C extension
     alone. This goes stale again on the next git pull.

"FileNotFoundError: groundingdino_swint_ogc.pth"
  -> Download the weights file (Step 3a) and place it in
     autoannotate study/GroundingDINO/weights/

"ModuleNotFoundError: No module named 'groundingdino'"
  -> Run: pip install -e "autoannotate study/GroundingDINO" (Step 4)

"error: invalid command 'bdist_wheel'" (Windows, STEP 4 build)
  -> pip install wheel setuptools, then re-run the STEP 4 install.

"fatal error C1189: ... /Zc:preprocessor" (Windows, CUDA >= 12.4/13)
  -> Update your checkout (setup.py now adds the flag automatically on
     Windows), or set it manually before building:
     $env:CL = "/Zc:preprocessor"

".cu compile error: no suitable conversion from DeprecatedTypeProperties"
  -> Fixed in the vendored source (value.type() -> value.scalar_type()).
     Pull the latest checkout and re-run the STEP 4 install.

"ImportError: DLL load failed while importing _C" (Windows)
  -> Python 3.8+ ignores PATH for extension-module DLLs. Make sure the
     CUDA_PATH environment variable is set (the NVIDIA installer sets it);
     the app auto-registers CUDA_PATH\bin at startup. Symptom if broken:
     DINO still runs, but slowly, on pure-Python deformable attention.

"AttributeError: 'BertModel' object has no attribute 'get_head_mask'"
  -> transformers 5.x is installed; GroundingDINO needs 4.x:
     pip install "transformers>=4.40,<5"

"DINO (SwinB) is greyed out in the Detector dropdown"
  -> groundingdino_swinb_cogcoor.pth (~938 MB) is missing; see Step 3a.

"DINO (SwinB) has a problem even though its weight is present"
  -> First run check_environment.py and save its full output. It now reports
     the installed torch build, CUDA runtime, GPU name/memory, and whether
     groundingdino._C imports. Then isolate checkpoint/config loading:
       python -c "from autoannotate.pipeline.dino import load_dino_model; m=load_dino_model('swinb'); print(type(m).__name__, sum(p.numel() for p in m.parameters()))"
     A successful result ends with GroundingDINO and 232903808. If that works
     but inference fails, capture the full traceback plus the image dimensions;
     the remaining likely class is CUDA/host-memory pressure, not a missing or
     mismatched checkpoint. On CPU-only Windows, use SwinT unless SwinB's
     accuracy is essential.

".env values seem ignored" / VS Code "python.terminal.useEnvFile" warning
  -> The editor warning is unrelated: the app loads .env itself via
     python-dotenv. Verify with check_environment.py, which prints the
     effective AUTOANNOTATE_MAX_AREA_FRAC and AUTOANNOTATE_SD_DEVICE.

"sam3.pt not found" or SAM3 entries greyed out
  -> Download sam3.pt (Step 3c) and place it in "GUI and Pipeline/".

"SAM3 text mode needs an ultralytics version that ships
 SAM3SemanticPredictor"
  -> Upgrade ultralytics:  pip install --upgrade ultralytics

"cannot connect to X server" / blank window on Linux
  -> You need a display. Use X11 forwarding or run locally.

"SmolVLM load failed" (on first use of Generate Prompts)
  -> The prompt-suggestion VLM couldn't load (out of memory, no network,
     etc.). It now loads lazily on FIRST USE, not on the splash, so this
     never blocks startup. Prompt generation just returns nothing; the
     rest of the app (Manual + Automated) is unaffected.

"No module named 'shapely'"
  -> pip install shapely

"No module named 'PyQt5'"
  -> pip install PyQt5
